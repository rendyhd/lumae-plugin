# Runner end to end (runner plan RN.8, RN.8b, RN.9), 2026-10-25

The plan's Verification list ([LUMAE_RUNNER_PLAN_2026-10-25.md](../plan/LUMAE_RUNNER_PLAN_2026-10-25.md))
run against the pinned stock host, with the plugin source of the RN.8 commit (on top of
`fd5551d`) mounted. Items 1–5 and 7 pass, after six fixes made on the way (below). Item 6,
R5's gate, did not pass at the representative scale, nor for a refresh that changes the
whole catalogue at the owner's scale. **RN.8b** (the owner's choice) moved the catalogue
work into a child process per action; with it R5 passes at both scales

## R5: the web process while the server runner works (RN.8, in the web process)

The probe pages the phone's v2 bootstrap (`/api/profiles/bootstrap/sessions/page`, 50
profiles a page, one request every 0.5 s), polls AudioMuse's `/api/active_tasks` every
0.5 s, and reads the gunicorn worker's RSS every 2 s. The gate: p95 within 100 ms of idle,
RSS within 300 MB of idle. Outside lookups were blocked (the synthetic albums would have
gone to MusicBrainz).

| Fixture | Work | Duration | Bootstrap page p95 (idle) | `active_tasks` p95 (idle) | Worst stall | RSS (idle → peak) | Gate |
|---|---|---|---|---|---|---|---|
| 132k | first refresh, every track changed | 309 s | 334 ms (95) | 137 ms (39) | 11.3 s | 270 → 3,002 MB | fail |
| 132k | refresh, nothing changed | 71 s | — | 421 ms (37) | 1.0 s | 289 → 1,359 MB | fail |
| 132k | relationship staging, with waveform passes (`heavy_work=server`) | 135 s | — | 217 ms (~40) | 3.9 s | 624 → 1,521 MB | fail (indicative) |
| 132k | waveform pass on the server (`heavy_work=server`) | 5 min | — | 42 ms (~40) | 86 ms | 624 → 656 MB (+238 MB in children) | pass |
| 37.5k | first refresh, every track changed | 77 s | 395 ms (94) | 138 ms (35) | 2.3 s | 239 → 992 MB | fail |
| 37.5k | refresh, nothing changed | 16 s | — | 101 ms (33) | 120 ms | 579 → 621 MB | pass |

- The first refresh is what the seeded fixture's pending identity transition ran
  (`identity_recheck` refreshes in `transition_pending`); the stand-in's songs give every
  track a new media fingerprint, so it publishes the whole catalogue as changed, as a first
  install or a rescan that changes every file does. That leaves the seeded profiles stale,
  so later bootstrap pages were empty and are not reported.
- The process keeps most of what the first refresh grew: 1.3 GB after the 132k one, 580 MB
  after the 37.5k one.
- The relationship build itself could not run on the fixture: it waits for AudioMuse's
  MusicNN IVF index, which the seeder does not build. The staging line mixes it with
  waveform passes.
- The waveform pass decodes in exec children, so the web process stays within the gate.

In 1.8.0 the catalogue refresh, the identity recheck and relationship builds ran in
AudioMuse's worker. In 1.9.0 the refresh, the preparation, the identity recheck and the
projection run in the web process by design (R1, so a new song reaches the phone with the
PC off), and the gate shows what that costs on a large or wholly changed catalogue.
R5's fallback covered only relationship builds; the owner chose to move all of that work
into a child process (RN.8b, below).

## R5 after RN.8b: catalogue work in a child process

Same fixtures, probe and machine, with `action_isolation`: the refresh, the preparation, the
finalization, the projection, the identity recheck and relationship build steps each run
in a child process started for them, at nice 10, which exits when they end. Each fixture
was seeded again for its first refresh. "Child" is the child process's peak RSS.

| Fixture | Work | Duration | Bootstrap page p95 (idle) | `active_tasks` p95 (idle) | Worst | Web RSS (idle → peak) | Child | Gate |
|---|---|---|---|---|---|---|---|---|
| 132k | first refresh, every track changed | 261 s | 88 ms (87) | 24 ms (29) | 225 ms | 273 → 293 MB | 2,827 MB | pass |
| 132k | refresh, nothing changed | 71 s | — | 23 ms (37) | 61 ms | 293 → 301 MB | 1,232 MB | pass |
| 37.5k | first refresh, every track changed | 72 s | 79 ms (89) | 21 ms (31) | 160 ms | 237 → 237 MB | 869 MB | pass |
| 37.5k | refresh, nothing changed | 17 s | — | 18 ms (34) | 42 ms | 237 → 237 MB | 414 MB | pass |

- The idle baselines before a first refresh overlap AudioMuse's own start-up, so requests
  during the refresh can measure faster than "idle"; the gate's margin holds either way.
- On the stock host with Navidrome: a refresh with a new song and an analysis run's
  finalization ran in children of the web process, and a relationship build step (`auto`)
  in a child of the worker; each child starts in under a second and grows to about 130 MB
  on that library. A child's log lines reach AudioMuse's log marked `(child <pid>)`.
- The gunicorn worker killed (SIGKILL) 15 s into a 132k refresh: its child died with it
  (`PR_SET_PDEATHSIG`); the new worker's runner, 2 minutes later, ran the preparation the
  interrupted scan called for (98 s, in a child), whose scan served the kept refresh
  request. The interrupted scan's row stays `scanning`, as it did when a process died
  mid-scan before.
- The memory is still used, by the child: a host with too little memory for its library
  gets the child killed, not AudioMuse's web process, and the action retries with its own
  back-off.

## RN.9: the re-cut archive on the stock host

The 1.9.0 archive `scripts/build_catalog.py` built from source (57 files), unpacked with
its catalogue entry, mounted and registered (`lumae-install register`), then both
containers recreated: both runners took the lead after their start-up delays (worker

reported 1.9.0 with `capabilities.journeys` and `edge_profiles.pending_requests: true`,
and a phone refresh (`/api/catalog/refresh`, 202 `queued`) ran in a child of the web
process that grew to about 130 MB and exited when the refresh ended (1.3 s).

## Fixed on the way

1. **A queued AudioMuse job held the runners.** R4 counted `NEW` jobs, so *Start analysis*
   with no worker paused the per-track passes until a worker came. Runners now step aside
   only for jobs a worker started.
2. **A Lumae job an older version left queued still blocked AudioMuse** (items 1). The
   install hook and the web process's start revoke `NEW` Lumae root tasks.
3. **The first preparation's by-design hold logged a traceback** on a fresh install
   (identity not yet resolved); it is a warning now, and the retry a minute later succeeds.
4. **A runner that went away kept its on-demand work for an hour** (half an hour for edges).
   Claims now name the runner's role; the role's next leader, or the server for a worker
   whose heartbeat stopped, puts them back to waiting.
5. **The status page did not show on-demand work while it ran**, nor credits, lookups or the
   projection: those announced themselves after the work.
6. **An unreachable MusicBrainz kept the server runner busy**: credits deferred one album,
   the next turn took the next album at once, about every 2 s with a journal event each
   (316 in 11 minutes). A turn whose actions moved nothing on now sleeps until the soonest
   retry: one album a minute, as 1.8.0's tick did.

The perf harness (`scripts/perf/stub_host.py`) also stubbed a function RN.6 removed.

## Notes

  avail` fails on a stale socket); recreate it (`up -d --force-recreate`). A host matter.
- Three tracks claimed before fix 4 waited for the stale-claim rule, which stays the backstop.
