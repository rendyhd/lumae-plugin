This is the first run of the P2-6 gate (`scripts/e2e/`, audit §3.3d) against
`phase/2-performance` cd298d7 (LumaeAnalysis 1.3.0, unreleased: Phase 1 plus

### kill -9 and restart at 6 points

The client runs v2 while the library changes through the real publication
path:

- **After the create:** 100 waveform republishes (each carries its edge),
  20 media changes (each a delete, then an upsert without an edge) and
  10 withdrawals (deletes).
- **At the snapshot end:** 20 edge publications.
- **Before the release:** 200 more waveform republishes, 10 media changes and
  5 withdrawals.

In total, 395 events happened during the sync. At each point gunicorn is
killed with SIGKILL and restarted:

- **Master and worker, then a new process.** After create, at the snapshot end
  and before release, the kill lands between requests and the client process
  is "killed" too; a new client resumes from the SQLite checkpoint.
- **Master and worker while a request is in flight.** Mid-snapshot,
  mid-catch-up and during deltas, the client retries that request.
- **On the stock host,** SIGKILL goes to the host's gunicorn master and worker,
  and supervisord restarts it.

**Two more kill points since the review (not in the full-scale numbers above).**
The harness now also kills the server *inside* both long captures, which P2-4
rewrites, and records for every kill whether a request was on the wire:

- **During the create's snapshot capture.** The runner holds ACCESS EXCLUSIVE
  on the published profiles table, waits until the capture's backend is
  blocked on it inside its capture transaction, then kills the server and
  releases the lock while it is down. The client's create gets no response
  and is retried with the same `client_request_id`; the orphaned `capturing`
  session is replaced (K5) and purged, not leaked.
- **During the first catch-up capture,** the same way on `profile_changes`.
  The retried catch-up captures again from `snapshot_seq`.
- In-flight kills now wait until the client's request is actually sent,
  instead of a 30 ms timer, and assert that every cut-off request failed on
  the client.

At scale 0.02 (JSON run `local_runner_scale_0_02_review_fixes`) all 8 points
fired: the 5 in-flight and in-capture kills each cut a request off (5
connection errors on the client), both captures were killed inside their
transaction, the create was retried once with the same `client_request_id`
and the orphan was deleted, one create served the whole run, and the device

once. The local host counts the two creators as different accounts, so the
rate limit does not bind. The stock host (`AUTH_ENABLED=false`) counts both as
`anonymous`, and the harness clears `profile_bootstrap_creates` between

|---|---|---|---|---|
| Create p50 / p95 / max | 7.8 / 8.7 / 8.9 s | 6.3 / 6.7 / 6.8 s | 5.3 / 9.7 / 9.8 s | 6.9 / 8.0 / 8.0 s |
| Statuses | 20 × 200 | 20 × 200 | 19 × 200, **1 × 503** (`Retry-After: 5`) | 20 × 200 |

A single create at 94k takes 4.0–4.3 s everywhere.

- **Same source.** The second creator waits for the first capture on the
  per-source lock, then captures itself. The two together come within about
  1 s of the client's 10 s timeout. Once, the wait passed the 5 s lock limit
  and the create got a 503.
- **Different sources.** The captures do not overlap usefully: each takes
  6–8 s instead of 4 s. They run on two threads of the one web worker process,
  and the capture loop is Python (`serialize_profile` and `json.dumps` per
  row), so they contend for the GIL. The same contention pushes the status
  routes over budget while the creates run.

A session is created. Then N upsert events shaped like `serialize_profile`
output are appended to the journal at once, and the first catch-up call is
timed. That call captures the interval on one web thread.

| Events | Kind | First catch-up | WAL (cluster-wide, upper bound) | Catch-up table | Peak RSS | Status routes p95 meanwhile |
|---|---|---|---|---|---|---|
| 100,000 | waveform only | 4.0 s | 150 MB | 90 MB | 172 MB | within budget |
| **1,056,000 (the cap)** | waveform only | **48.3 s** (46 µs/event) | 1,652 MB | 959 MB | 174 MB | 26 / 31 / 39 ms |
| 1,056,000, client timeout 10 s | waveform only | first page after 50.1 s: 1 timeout, 4 × 503 `Retry-After: 5`, then 200 | 1,264 MB | 959 MB | 172 MB | 27 / 38 / 47 ms |
| 20,000 | each embeds its 19.5 KB edge | 7.4 s (370 µs/event) | 485 MB | 112 MB¹ | 176 MB | within budget |

¹ Includes the index left by the previous (1,056,000-event) run; the rows
themselves hold only the waveform part, because the capture splits each edge off
into a reference (K2).

- The cap was measured directly, not extrapolated. It is about 4× faster than
  the P1-5 review's estimate (3.5–4 min for 752k events). Memory does not
  grow, because the capture streams in 500-row batches.
- A client with the app's 10 s fast-fail still gets its first catch-up page
  about 50 s after asking, through the existing `Retry-After` handling, and
  keeps its session.
- **Edge-carrying events.** Linear extrapolation, labelled as such: if an
  entire capped interval were edge-carrying upserts (a LUM-005 regeneration
  before K6), the capture would take about 6.5 min, and the journal would
  hold tens of GB of edge copies. K6 (P3-2) and the P3-1 ordering exist to prevent exactly
  that.

## Findings

1. **Plugin performance bug: the v2 page query does work proportional to the
   rest of the snapshot when its statistics are missing.**
   `profile_bootstrap.snapshot_page` selects `FROM profile_bootstrap_snapshot s
   LEFT JOIN LATERAL (edge lookup) … WHERE session_id=… AND ordinal>=…
   ORDER BY ordinal LIMIT page_size`.

   **When it happens.** The table has no column statistics: a fresh install,
   or before autovacuum has analysed it. The planner then estimates a few rows
   and chooses:
   - a Bitmap Heap Scan of **every remaining row** of the session;
   - the LATERAL edge lookup and `jsonb` concatenation for each of them, which
     detoasts every edge;
   - a Sort, and only then the LIMIT.

   Page cost is therefore O(remaining rows).

   **Measured:**
   - Local runner, 1,880 profiles (scale 0.02), freshly seeded, recorded with
     `--explain-analyze` (JSON runs `local_runner_scale_0_02_no_snapshot_statistics`
     and `…_analyzed_snapshot_statistics`). Without statistics, `EXPLAIN ANALYZE`
     of page 0 took 201.4 ms (Bitmap Heap Scan of 1,880 rows, 1,880 edge
     lookups, Sort) and mid-snapshot 88.5 ms (930 lookups). The first 10 pages
     had p50 205 ms, the last 10 76 ms, and the v2 first load took 8.3 s. After
     `ANALYZE` of the table while a session existed, the same queries took
     6.5 ms (Index Scan, 50 lookups), pages 58 ms p50 throughout, and the first
     load 4.7 s.
   - Stock host, fresh bundled PostgreSQL 15, 4,700 profiles: the first 10
     pages had p50 1,331 ms, until autovacuum analysed the table mid-run and
     the plan flipped (last 10 pages: 115 ms). The v2 first load took 41.0 s
     against 18.2 s for legacy.
   - Stock host, fresh PostgreSQL 17: first 10 pages p50 550 ms against 70 ms
     at the end. The v2 first load took 36.7 s against 11.5 s for legacy.

   **At 94k,** the planner chose the ordered index scan in every full-scale
   run whose plan was recorded (estimate 1,028 rows on the fresh table), and in
   every full-scale v2 run the first and last pages cost the same (about 60 ms
   p50), so the full-scale gate is unaffected. But the plan choice is
   statistics-dependent, and a wrong choice on a mid-size library would make
   every page cost seconds, and could hit the 20 s statement timeout (503).

   **Same shape elsewhere.** The catch-up page query has the same form.

   **Fix, not done here (this WP adds no plugin code):** take the `ORDER BY
   ordinal LIMIT` in a subquery before the LATERAL join, for both queries.
   `run_server_matrix.py` records the planner's choice
   (`page_query_plan`) in every v2 first load.
2. **v2 captures are CPU-bound on the web worker.** See the creators table: two
   concurrent captures share one GIL. This is the root cause of the P2-4 miss.
3. **The stock image cannot produce edges.** It ships PyAV 17.1.0, and the
   plugin's edge analyzer requires 16.1.0 with libswresample 6.1.100. On a
   stock host, `capabilities.edge_profiles.available` is therefore false and no
   new edge is analysed unless the operator installs `requirements-edge.txt`
   (as `EDGE_PROFILES.md` says). Serving existing edges is unaffected. This is
   an operability note, not a bug.
4. **Retry behaviour held.** No 429 appeared in any scenario. The 503s seen (one
   concurrent create, the short-timeout catch-up retries) carried
   `Retry-After: 5`, and no client request needed a missing-header fallback.

## P2-4 recommendation

The plan closes P2-4 only if all three conditions hold. They do not:

| Condition | Measured | |
|---|---|---|
| Create ≤ 5 s | 4.0–4.3 s alone. With 2 concurrent creators: 6.7–9.7 s p95 | **no** |
| No 503 under 2 concurrent creators | 0 / 40 locally; 1 / 40 on the stock host | **no** (stock host) |
| Capped catch-up acceptable | 48–50 s at the full 1,056,000-event cap, flat memory, status routes in budget, recovers through `Retry-After` | yes |

**Recommendation: implement P2-4, as a server-internal change and not the
asynchronous design.**

- **Build the rows in SQL.** Build snapshot rows (and the first catch-up's
  rows) inside PostgreSQL with `INSERT … SELECT`: option (b) without RQ,
  instead of a Python loop per row. The captures then run in separate backends
  in parallel and stop holding the web worker's GIL, which also takes the
  status routes back under budget.
- **Keep statements bounded.** Batch by `track_id` or `seq` range: the
  1,056,000-event capture takes 48 s in total, and each statement has a 20 s
  `statement_timeout`.
- **Keep the output identical.** An equivalence test must show byte-identical
  output with `serialize_profile`: float4 `ref_lufs`, zone-less
  `analyzed_at` (including a whole-second value), and base64 ramps without the
  line breaks PostgreSQL's `encode` inserts.
- **Acceptance.** Re-run `run_server_matrix.py --scenarios
  creators,capped_catchup,first_load_v2`: with 2 concurrent creators, create
  p95 ≤ 5 s and no 503.
- **Not the 202 + RQ path.** A single create already fits, and the capped
  catch-up finishes within a minute with the client's existing handling. That
  path would add a capability flag, a contract entry and C-3 client work
  without addressing the measured cause.
- **Not option (a)** (paging the catch-up straight from the journal): the
  measured copy cost is acceptable.

The page-query fix in Findings item 1 is independent and small, and fits in
the same WP or its own.

## Caveats

- **The client is a simulation.** `client_sim.py` follows the contract and the
  hand-off but is not Auralscape. Its CPU, SQLite and memory figures are
  indicative only; C-8 measures the real app.
- **Synthetic fixture,** as in P0-3. Edge payloads have real size and
  structure with per-track variation; ramps are 45 bytes.
- **Shared machine.** Another work package's benchmark (one core at about 90%)
  ran from about 11:15 UTC. It overlapped the capped catch-up and the bundled
  PostgreSQL 15/17 runs, but not the full-scale local (09:46–10:27) and
  stock-host (10:46–11:13) runs. WAL figures are `pg_current_wal_lsn()` deltas
  on the shared cluster, so they are upper bounds.
- **Bridge-network runs.** The bundled PostgreSQL 15/17 runs used Docker's
  bridge network and the userland port proxy under that contention. Their
  status-route latencies (for example `/api/catalog/health` p95 120–156 ms
  during a 4.7k first load) are not budget measurements. They validate the
  compose files and the plugin on PostgreSQL 15 and 17; every functional check
  passed on both.
- **Harness-only behaviour.**
  - Between scenarios and creator rounds the runner deletes
    `profile_bootstrap_creates` (the K4 rate limit is 6 creates per 10 minutes
    per source and caller).
  - The local host maps a harness header to separate accounts.
  - The "different sources" creator run adds a second source that copies the
    published rows. Its edge rows keep the real key columns but carry a tiny
