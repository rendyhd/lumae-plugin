# Runner end to end on the owner's server and both stock hosts, 2026-10-27

The re-cut 1.9.0 (`17c68beb70c63796b7ced4479aaad25f`, commit `83d1d88`) tested two ways:
live on the owner's server, and on a local stock-host harness on the pinned v3.6.3 image
and the devel image (v3.7.0). Everything the runner plan promises held, except two bugs
(below): a NOTIFY from another process can wait up to 30 s, and the upgrade's revoke misses
a 1.8.0 task queued through the plugin API. Both are fixed in the re-cut that followed,
with the relationship build's checkpoint logging ([Fixed after the run](#fixed-after-the-run)).

## Bugs

1. **A NOTIFY from another process waits for the next heartbeat (up to 30 s).** `_lead`
   heartbeats on the LISTEN connection before it waits (`runner.py:315`); that query reads
   a pending NOTIFY off the socket into `conn.notifies`, and `_wait_for_wake` only looks at
   `notifies` once `select` says the socket is readable (`runner.py:356-361`), which it no
   longer is. Seen live: a forced rebuild waited 35 s. It delays the web's wakes of the
   worker (on-demand, rebuild) and the song hook's wakes of the server (finalization).
   Reproduced by `test_a_notify_from_another_process_during_a_turn_still_wakes_the_leader`
   (`tests/plugins/test_runner_postgres.py`, fails 3 of 3; the suite's 0.5 s heartbeat had
   hidden it). Fix: check `notifies` before each `select`.
2. **The upgrade's revoke misses a 1.8.0 task queued through the plugin API.** It matches
   only `plugin.lumae_analysis.%` (`__init__.py:579`, `:623`), the cron names. 1.8.0
   queued phone, on-demand and preparation work with `plugin.api.enqueue`, which the host
   names `plugin.audiomuse_plugins.lumae_analysis.<task>` (`plugin/api.py`, `dotted_path`
   and `task_type=f'plugin.{dotted}'`, both images). Reproduced on v3.7.0: a 1.8.0 phone
   refresh with no worker left `...catalog_refresh_task` `NEW`, and after the upgrade
   *Start analysis* still answered 1201 until the task was cancelled. The tests cover only
   the cron name (`test_reconcile_scheduler_postgres.py:590-609`). The owner's server has
   no such row, so it is not affected now.

## Observations

- The lane is fixed for a turn (up to `RUNNER_TURN_SECONDS`, 300 s), so after switching
  back to `auto` with a worker online the server kept the heavy work up to 5 min.
- Nothing wakes the worker when the server lets go of a build: after a manual
  `server` → `auto` switch mid-build the worker sat idle 10.7 min. Only a manual switch
  causes it.
- After the server decoded an on-demand track, the pooled analysis worker (244 MB, nice 0)
  stayed in the web container; R5 asks for nice 10 for the server's work.
- Steps cut by a Flask restart are recorded `failed` (`ChildFailed`, SIGTERM) rather than
  `interrupted`; the build retried them correctly.
- The settings page's edges left is still about 8k high on the owner's server: a VACUUM's
  extrapolated count, which the next ANALYZE corrects.

## Fixed after the run

Before the second re-cut of 2026-10-27, each with a test that fails without it:

- Bug 1: `_wait_for_wake` looks at `notifies` before each wait on the socket.
- Bug 2: the revoke also matches `plugin.audiomuse_plugins.lumae_analysis.%`
  (`LUMAE_API_TASK_PREFIX`), still only `NEW` root rows.
- The relationship checkpoint line, reported from the owner's Flask log: 3,115 lines
  at INFO in one build, up to 41 a second, 13 % of the log. A build now logs its start
  and each new phase at INFO and the checkpoints between at DEBUG.
