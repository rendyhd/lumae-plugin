# Performance baseline — 2026-09-24 (P0-3)

This is the first run of the `scripts/perf/` harness. It measures the plugin
code at `phase/0-foundation` cb46213. The `plugins/` code there is identical
to `main` 746a7b8 (LumaeAnalysis 1.2.5 source), so this is before any
Phase 1/2 performance work. Later performance WPs report before/after numbers
against this baseline (plan §1.2 item 5).

Current code is expected to miss most budgets, and it does. The baseline
records by how much.

- Raw results: [`BASELINE-2026-09-24.json`](BASELINE-2026-09-24.json)
  (written by `run_baseline.py --out … --diagnostics`)
- Re-evaluate: `python3 scripts/perf/run_baseline.py --from docs/perf/BASELINE-2026-09-24.json`

The JSON's `git_sha` field says 49b7428: the harness commit before the review
fixes. The plugin code it measured is the same.

## Breakdown and diagnostics

**Publication (`pub_bench.py`, 40 iterations).**

| Step | p50 | p95 |
|---|---|---|
| `record_profile_change` (append and compaction) | 13.2 ms | 16.4 ms |
| the same, with commit | 14.0 ms | 17.1 ms |
| compaction `DELETE` alone | 11.5 ms | 17.1 ms |

- The journal stayed at exactly 50,000 events.
- `explain_journal.sql` shows why. The compaction predicate
  `epoch<>$1 OR (epoch=$1 AND seq<=$2)` plans as a **Seq Scan** of the 50k-row
  journal (15.4 ms). The equivalent range-only form uses the primary key
  (0.12 ms).

**Health and settings SQL (`explain_health.sql`).**

| Query | Time |
|---|---|
| `_coverage` (tracks × map × chromaprint) | 400 ms |
| `analysis_status_counts` (settings poll) | 244 ms |
| `_link_coverage` | 48 ms |
| AudioMuse active-task probe | 27 ms |
| task evidence | 2 ms |

With the coverage SQL stubbed (`route_floor.py`), `/api/catalog/health` costs
**6.6 ms** p95. Nearly all of its latency is the coverage query.

**Bootstrap concurrency (`boot_concurrency.py`).** A second creator started
0.5 s after the first gets `bootstrap_unavailable/503` after 5.0 s: it waits
on the global advisory lock until `lock_timeout` fires. The first creator
fails with the 413 above. The plugin-owned connection setup costs 3.3 ms p50
and 4.8 ms p95 per call, and this is included in every page time.

**Collections feed (`feed_contention.py`, 300 tx per writer).**

| Append | 1 writer | 8 writers |
|---|---|---|
| sequence | 1,421 tx/s, p95 1.3 ms | 4,031 tx/s, p95 3.9 ms |

## Caveats

- **Scale.** This run is at full scale (1.0), so no fallback to 0.25 was
  needed. `run_baseline.py` refuses to judge scale-dependent budgets on a
  smaller fixture unless `--allow-scale` is passed.
- **Synthetic fixture.**
  - Metadata strings, embeddings and chromaprints are generated.
  - Edge payloads have real size and structure, with per-track variation in
    ids, noise floor, levels (signed centidB) and per-bin jitter.
  - Profile ramps are 45 bytes, as in the audit fixture.
- **The bootstrap page PASS needs context.**
  - At production limits, a real-edge v2 snapshot cannot be created at all:
    it passes 128 MiB within about 6k profiles.
  - The page numbers therefore come from a create with `MAX_SNAPSHOT_BYTES`
    and `MAX_SNAPSHOT_ROWS` lifted (`pages_from: create_lifted`).
  - At page_size 50, each page is about 1 MB of JSON.
- **WAL figures are cluster-wide.**
  - The `wal_mb` fields in the JSON measure `pg_current_wal_lsn()` deltas on
    a PostgreSQL cluster shared with other databases, plus autovacuum after
    the bulk load.
  - The no-change projection reports 581 MB of WAL for 9 statements, so none
    of it is the projection's own. Treat these fields as upper bounds and
    compare WAL only on an otherwise idle cluster.
- **Measurement method.**
  - Route latency is measured through the Flask test client, so it includes
    no HTTP server or network.
  - Page time is the `snapshot_page` call, including the plugin-owned
    connection setup.
  - Lock hold is sampled from `pg_locks` every ~2 ms.
- **Fixture mutations.**
  - `projection_delta` leaves generation 2 in place.
  - `pub_bench.py` appends 82 journal events: 41 through `complete_attempt`,
    which also drops those tracks' edges, and 41 through
    `record_profile_change`.
  - Later runs on the same fixture are therefore not pristine. Re-seed before
    comparing.
- **Machine.**
  - Single run on a shared 4-vCPU container.
  - Expect ±10–20% run-to-run noise. A first run with the over-stubbed
    migration gave numbers within about 10–35% of these. Budget misses here
    are 3.6× or more.
