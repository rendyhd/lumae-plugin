**Lumae plugin review — 5 September 2026**

The catalogue/profile foundation has useful protections: source-scoped identities, atomic publication, preserved generations, bounded normal audio analysis, and conservative defaults for optional DJ playback. Radio DJ V3 needs another correctness and integration pass before broader use. Its strongest regressions concern speech-cut evidence, concurrent job ownership, recovery scheduling, and candidate selection. Passing the current tests does not establish those guarantees.

Findings about Friend Album Discovery below apply to that WIP source, not the published Lumae Analysis 1.1.8 zip.

**Confirmed findings, in priority order**

1. **[P1] Constant high-risk speech is declared safe to cut.** In [dj_analysis_v3.py:227](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis_v3.py:227), speech activity passes through percentile normalization. `_normalized` returns all zeros when its input has no dynamic range. The subsequent `<=` comparisons accept the entire constant region as a quiet minimum and its guards. A probe with constant positive band energy and calibrated speech risk **0.99** produced a “speech-safe” interval from **4,260–5,760 ms**, and `_safe_at(5000)` returned `True`. Reject flat/degenerate evidence and require an actual local reduction with a defensible absolute or contextual floor. Calibration of YAMNet scores does not validate this separate speech-minimum heuristic.

2. **[P1] V3 bypasses explicit cut authorization.** [dj_analysis_v3.py:280](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis_v3.py:280) accepts a low calibrated score without checking `calibration.cuts_authorized`. The speech-minimum branch checks authorization, but this branch does not. A full payload built with a valid reviewed calibration artifact and **`authorize_cuts=False`** still contained **eight cut candidates and eight `loop_verified=True` candidates**. The current global playback capability remains unavailable, which limits public exposure, but the producer contract is internally contradictory and unsafe for consumers that trust these fields. Enforce authorization before emitting safety/verification flags and cut eligibility, and retain risk measurements separately.

3. **[P1] Recovery can take ownership from a live worker.** [dj_analysis_v3_store.py:166](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis_v3_store.py:166) resets *every* running V2/V3 row to pending at every claim. The transaction advisory lock serializes the short claim transaction; it does not protect the analysis lifetime. With two real database connections, both claimers obtained the **same track and same token**, with attempts 1 and 2; the first worker was still reported as not cancelled. If a higher-priority job arrives, the two processes can instead analyze different tracks concurrently. The inspected private image starts one DJ process per container, but its queue claim SQL supports multiple consumers and has no global queue mutex. Use a session lock or an expiring ownership lease, reclaim only demonstrably abandoned work, and issue a new fencing token for each ownership transfer. Do not depend on a single-container topology for correctness.

4. **[P1] Deferred durable DJ jobs have no automatically installed wake-up schedule.** [__init__.py:3414](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/__init__.py:3414) returns when profile work is pending, without scheduling a retry. Enqueue failures similarly rely on comments promising a watchdog. [__init__.py:6719](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/__init__.py:6719) only declares a selectable cron task. Migration creates schedules for other maintenance tasks but no DJ schedule; the existing migration test explicitly asserts that set. The inspected private worker periodically calls `attest_dj_worker_capability`, which does not enqueue pending analysis. Unless an administrator separately creates the cron row, a deferred request can remain pending indefinitely after ordinary work clears. Install an opt-in, bounded DJ reconciliation schedule or have the core dispatcher consume the durable queue directly, including wake-up after enqueue failure and restart.

5. **[P1, release pipeline] Private source on main prevents the public catalogue build.** The public builder packages the current plugin directory and rejects changes to an already checksummed version at [build.yml:173](C:/Users/rendy/vscode/lumae-plugin/.github/workflows/build.yml:173). Source metadata still names 1.1.8, while the directory now includes the DJ changes. The stored 1.1.8 archive matches its published checksum; rebuilding current source does not. The local candidate hash was `7e05f87aade1ba46e15e9353b5b12768`, versus declared `6a0196e20d33f8be21b9551c02a009e2`. Therefore the build fails before it can publish the catalogue, including another plugin release. Preserve the immutability guard, and separate private development from the public release source selection. Bumping a public version just to make CI green would defeat the stated private-channel intent.

6. **[P2] Unsupported/failed V3 work can be requested repeatedly without backoff.** [dj_analysis_v3_store.py:147](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis_v3_store.py:147) replaces any terminal job immediately and resets attempts to zero. V2 has a six-hour terminal-state backoff, but V3 lost it. Immediately after finishing a job with `rss_cap_exceeded`, a second request was accepted. A client retry loop can repeatedly consume the worker on the same unsupported or resource-heavy file. Persist retry timing and distinguish permanent unsupported results from transient failures; invalidate them on relevant source/producer/calibration changes or explicit force.

7. **[P2] Overlapping regions consume the cue budget with duplicate timestamps.** Deduplication at [dj_analysis_v3.py:342](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis_v3.py:342) includes `region_index`, so the same musical boundary survives once per overlapping region. Selection at line 442 then takes the first eight entries. The ordinary 192-second fixture produced exit rankings `[184000, 184000, 184000, 176000, 176000, 176000, 168000, 168000]`: **eight slots, three distinct exits**. Merge evidence for the same role and temporal boundary before ranking, keeping region provenance as supporting evidence. Add minimum cue separation if the client needs meaningful alternatives.

8. **[P2] Region truncation drops the end of supported long tracks.** [dj_analysis_v3.py:200](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis_v3.py:200) sorts regions chronologically and takes the first 64 before cue selection. A supported 30-minute, 120-BPM fixture retained regions only through **1,040 seconds**. Exit eligibility begins at 65% of the track (**1,170 seconds**), so it produced **zero exit cues** despite regular rhythm throughout. Preserve tail coverage when selecting regions, or compute cues across the full timeline before applying a coverage-aware output budget. The same principle applies to the first-256 band windows and first-128 structural boundaries.

9. **[P2] Cancellation checks create excessive synchronous database traffic.** [dj_analysis.py:154](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/dj_analysis.py:154) calls cancellation on every decoder frame and inference window; the worker binds that callback to a database query at [__init__.py:3453](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/__init__.py:3453). A real 60-second WAV decode generated **649 Beat This checks plus 770 YAMNet checks**, or **1,419 SQL queries per source minute**, before other database work. Query count varies by codec/frame size. At 5 ms per serial round trip, that count alone represents approximately 7.1 seconds per source minute; this is an estimate, not a measured deployment latency. Keep local deadline checks frequent, but throttle database cancellation/lease checks by wall time, such as every 250–1,000 ms, or use a cached cancellation signal. Avoid leaving a read transaction open across long compute phases.

10. **[P2] Model removal runs on the web host rather than the dedicated model host.** [__init__.py:6584](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/__init__.py:6584) calls filesystem deletion directly from the settings request. The capability design explicitly supports Flask and DJ workers on separate hosts, and provisioning runs on the worker. Without a shared model filesystem, the action disables analysis but leaves the worker's downloaded models intact, while reporting a completed removal action. Dispatch removal to the model-owning worker under the provisioning lock and report its durable result. Coordinate it with in-flight setup so a download cannot recreate a just-removed artifact.

11. **[P2] V3 has a cancellation checker but no matching cancellation API.** The only cancellation handler, [__init__.py:3392](C:/Users/rendy/vscode/lumae-plugin/plugins/LumaeAnalysis/__init__.py:3392), calls the V2-only `cancel_dj_jobs`. V3 requests and storage are separate, and no V3 cancel route updates those rows. Calling the legacy route cannot cancel a V3 track. Add version-aware cancellation with a stable response, and test queued and running V3 cancellation through the actual Flask route and database.

12. **[P2] CI omits important deterministic DJ validation.** The explicit test list at [build.yml:69](C:/Users/rendy/vscode/lumae-plugin/.github/workflows/build.yml:69) excludes `test_dj_coverage.py`, `test_vocal_calibration.py`, and `test_private_vocal_review_pack.py`, even though these govern qualification inputs and reports. Changes under `scripts/` alone do not trigger the workflow either. Discover the complete plugin suite, include script paths in triggers, and retain PostgreSQL execution. Add targeted tests for the reproduced failures above: the current V3 recovery test asserts the unconditional reset SQL rather than proving that a live owner cannot be reclaimed. Actual model inference needs a separate optional runtime qualification job; metadata and mocked-adapter tests do not establish inference correctness or RSS behavior.

15. **[P2] Interactive federation requests do full-catalogue work, including an N+1 query.** [FederatedAlbums/__init__.py:625](C:/Users/rendy/vscode/lumae-plugin/plugins/FederatedAlbums/__init__.py:625) calls `_instance_id()` once per local album, and that helper performs a SQL query each time. 16. **[P2] Remote pagination can occupy a Flask request indefinitely.** [FederatedAlbums/__init__.py:726](C:/Users/rendy/vscode/lumae-plugin/plugins/FederatedAlbums/__init__.py:726) has no page-count limit, cursor-progress check, or overall deadline. Per-request socket timeouts do not bound an unending sequence of successful page requests.

**Architecture assessment**

The existing layering is partly effective: provider adapters and identity guards isolate changing provider IDs; catalogue, analysis, profile, and relationship streams have published generations; optional edge and DJ results are source-bound; and the heavier DJ packages are loaded lazily. Atomic source/token checks on publication are worth retaining. Normal waveform decoding and bounded IVF candidate selection also address the right performance risks.

The main composition module now spans **6,719 lines**, combining migrations, HTTP routes, queue orchestration, worker setup, capability negotiation, and HTML rendering. V3 imports V2's private helpers and runs the complete V2 annotation builder before replacing much of its output. Two parallel job stores duplicate lifecycle logic and have already diverged in retry, promotion, and cancellation behavior. These are concrete reasons to separate responsibilities, beyond file size alone.

A practical target structure is:

| Responsibility | Suggested boundary |
| --- | --- |
| HTTP/settings | Thin routes with validation and explicit service calls |
| Job lifecycle | One version-aware queue repository with ownership, retry, cancellation, and wake-up invariants |
| Audio/model execution | Shared decoder/runtime adapters producing immutable raw evidence |
| Analysis contracts | Independent V2 and V3 projections over that evidence |
| Capabilities | Worker identity, supported host API, artifacts, calibration, and qualification as distinct states |
| Publication | One transaction boundary for current source, ownership, payload, and readiness |

Keep public contract versions independently readable while sharing job mechanics. Avoid deleting V2 merely to reduce duplication. A producer/cache identity should include every change that affects usable output, including analysis method, model and calibration hashes, and relevant decoder/representation assumptions.

The private worker image is currently part of the feature's effective architecture. It adds `lumae-dj` routing and periodically calls a plugin-specific attestation function. Installing the Python requirements alone does not provide those host behaviors. Make that integration an explicit, versioned host capability so the plugin can explain a missing queue/attestation contract accurately and cannot silently route heavy DJ work onto a stock default queue. The plugin's `enqueue_bounded` also discards the timeout argument; internal analysis deadlines therefore must not be presented as proof of an end-to-end job timeout covering provisioning and media acquisition.

**Performance assessment beyond the confirmed defects**

The DJ adapters spool PCM to disk and use fixed inference windows, which controls waveform allocation. However, each analysis currently reads/hashes the source, decodes it once for Beat This and again for YAMNet, and reconstructs/verifies both model adapters per job. Requesting both V2 and V3 for the same representation repeats inference. These are optimization candidates, not measured bottlenecks: first profile source acquisition, model setup, each inference stage, annotation, and publication on the intended host. Consider shared raw evidence and decode fan-out where the memory budget permits. Weigh warm model reuse against the fault isolation of a process per job.

Payload budgets need byte and timeline semantics as well as array limits. The synthetic V3 payloads measured approximately **75 KB for 192 seconds** and **343 KB for 30 minutes**, without a populated vocal-risk timeline. An endpoint accepting 100 IDs can therefore produce a substantial response. Measure populated payloads and database serialization, and consider byte-limited pages, compressed transport, or compact timeline encoding. Do not obtain smaller payloads by dropping every late-track region.

Normal relationship matching uses a bounded shortlist, but its input loader still materializes the source's complete track/embedding set. This deserves a large-library memory benchmark independently of the DJ 1 GiB policy. Optional edge/DJ tables also deserve explicit deleted-track retention/pruning rules; their foreign keys are to catalogue sources, not individual current tracks.

**Overall design and evidence semantics**

- The settings panel says **Ready** once the runtime/artifacts are available, even when calibration or playback qualification is absent. Show separate “worker ready,” “analysis progress,” and “playback qualification” states, including the reason and next useful action. A disconnected worker should not look indefinitely like an active download.
- `loop_verified=True` is based on a scalar energy seam comparison, not a rendered PCM seam or phase-continuity check. Keep it as candidate evidence until the appropriate verification occurs.
- V3 replaces exact natural start/end with percentile-normalized model-envelope positions. The 192-second ramp fixture reports a natural entry at **14.8 seconds**. Preserve exact source beginning/EOF separately from suggested audible boundaries; low relative energy is not padding evidence.
- V3 sets `timeline_verified=True` for every decoded source, while EdgeProfile limits that claim to declared lossless paths. Define the scope of verification and retain the requirement to match the actual playback representation/decoder before precise cuts.
- The coverage evaluator collapses cue roles and tempos into track-wide sets, so it can match a high-confidence tempo from one region to a cue in another and does not check cue-level speech safety. Treat its current tier counts as optimistic availability estimates, not proof that the actual planner can execute the transitions. Prefer evaluating real candidate pairs using the planner's eligibility predicates.
- The federation addition duplicates album-dynamics and identity/scoring concepts already present in catalogue enrichment, and reads core tables directly without the existing source-scoped adapter boundary. Reuse a documented source projection and shared golden fixtures so multi-server support and ranking semantics do not drift independently.

**Recommended order of work**

First fix producer authorization/speech safety, job ownership, and durable wake-up behavior, with regression tests that fail under the current implementation. Restore a working separation between public release builds and private DJ development. Next correct cue diversity/tail coverage and complete V3 lifecycle controls. Then throttle database polling and measure actual inference and response costs before changing the runtime architecture. Finally extract the shared lifecycle/evidence services and qualify a representative audio corpus, including speech, flat/quiet passages, irregular rhythm, and long tracks. Friend Album Discovery should remain separate WIP until installation and ownership checks pass.
